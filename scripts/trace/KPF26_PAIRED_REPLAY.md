# KPF-26 paired replay scaffold

`kpf26_paired_replay.py` executes an explicitly supplied, digest-pinned executor twice in the manifest's order. The executor is a separate integration boundary: it must run the same frozen tasks against the real scout path, independently read back server flags and identities, capture each child outcome and timing, and record actual checkpoint/fork and interval occupancy witnesses. Its command interface is `EXECUTOR --manifest PATH --arm off|on --evidence PATH`. Stdout/stderr and returned evidence are retained verbatim in a new output directory; interrupted, failed, duplicate, missing or partial evidence is invalid. It does not configure or reload a serving process.

Manifest `epyc.kpf26.paired.v1` pins request and scorer-input files (path and sha256), unique task IDs, sibling count, model, server binary digest, source commit, server argv, executor digest, arm order, a per-arm timeout and a prospective maximum occupancy-sample interval. Evidence must echo those pins and the original manifest digest; both arms must use distinct windows and state the one-skip flag configuration. For every task, executor evidence supplies start/end, occupancy samples spanning the interval, and one record per distinct child with output digest, scored outcome, admission wait, TTFT and prefill tokens. The on arm also supplies one observed trunk/checkpoint witness and a task/slot-bound positive fork witness for each child. Missing or invalid fields produce `INVALID`, never a pass.

`OBSERVATION_COMPLETE` means only that the supplied evidence has the required shape; this scaffold cannot independently authenticate arbitrary executor assertions, and it does not decide the scientific gate. A real executor must bind and retain native server/slot, output, window/grant and sampled occupancy sources and emit the established VB-KVU-PF native records at collection time. Actual flags, binary/DSO provenance, role, cohort, scoring, sampling policy, baseline and non-regression rule must be independently qualified before any run or decision. The test executor is entirely synthetic and cannot satisfy a real gate; the separately implemented real-stage executor is described below.

`kpf26_scout_executor.py` invokes the actual `run_scouts` path for a request containing `spec` (one turn and the manifest's exact number of targets), `scope_root` and a complete `scope_files` SHA-256 map. Each expected file supplies either exact `summaries` or a `epyc.kpf26.scorer.required-terms.v1` list of required terms in scout order. The scorer is pinned by the manifest; missing summaries remain unknown. `runtime.off` and `runtime.on` specify a numeric-loopback server URL, role, PID, distinct window ID, occupancy sample interval and `grant_id`. The process must run inside the matching filler launcher with an active canonical rowflow grant, consistent hard end and stop/deadline controls. The executor hashes the live grant at both boundaries and refuses changed or revoked grants. It binds the endpoint's actual listening socket inode to the pinned server PID at both boundaries; network proxies are disabled.

The executor verifies the source commit, clean tracked tree, actual server process/binary/argv, mapped llama/ggml library digests and model path; it retains before/after process identity, `/slots` samples, per-call timings and raw scout summaries. It binds checkpoint/fork witnesses only when matching slot/task identities are observed during the relevant call; missing evidence stays null. Scope symlinks or file drift refuse. A valid completed arm writes native `epyc.kpf.run.v1` rows to `belief_measurements.jsonl` at collection time for the existing KV prefix-fork adapter; no gate or quality verdict is inferred.

A real coordinated window, a separately declared manifest and scientific gate rule, original write-side ingest, and a planning-context canary are still required; mock tests do not establish those results. No inference has been performed by the implementation tests.

`kpf26_prepare_smoke.py` makes a **prospective smoke**, derived from the retained 2026-09-27 HS-19a codename fixture. It freezes the original prompt and file, transforms the original one-subagent lookup into two new scouts, binds the actual local server process, full model bytes, binary, executor, source, role and future grant ID, and makes distinct off/on window labels. Its hash-pinned deterministic scorer checks the literal fact and identifier in each summary. This is not a historical scout replay, a substitute for the required through-:8000 KPF-26 gate, or a quality/generalization claim. Prepare only against the intended private fork-capable server; the preparer makes no inference and does not create a grant. Example:

```bash
python3 scripts/trace/kpf26_prepare_smoke.py --output /path/to/new/packet \
  --server-pid "$SERVER_PID" --url http://127.0.0.1:18971 \
  --role architect_critic --model /absolute/model.gguf --grant-id "$ROW_ID"
# Later, inside that same active, bounded owner-issued grant:
bash scripts/trace/kpf26_run_smoke.sh /path/to/new/packet
```

The preparer refuses a dirty source checkout, existing output, mismatched model/server or absent mapped ggml; the executor independently rechecks these, the grant and socket at execution. The predeclared required-term scorer is a diagnostic fact check, not a change to any outcome rule. Both arms currently run sequentially inside one grant and use distinct logical window IDs; they are not independent granted windows. The API-level `:8000` replay and two independently qualified decision windows remain separate requirements.

The same packet also pins `api-request.json`, a valid `ChatRequest` for `POST /chat` with scoped scouts and an explicit task-root. `kpf26_api_smoke.py --packet PACKET --api-url http://127.0.0.1:8000 --api-pid PID --output NEW_DIR` sends **one actual API request**, only within the bound live grant. It binds both listening sockets and server/model bytes, adds a request-level deadline before the grant expires, records the full API response and sampled `/slots`, and detects process/grant identity changes. It records flags as unknown and deliberately does not score summary previews: the API does not return full scout summaries. Its `API_SCOUTS_OBSERVED` means only the route reported all requested scouts complete. It is not a paired experiment, a verified fork, a scored outcome, or the KPF-26 gate; no API reload is attempted.

For private, request-scoped API scout evidence, the API process can be started by its owner with `ORCHESTRATOR_KPF26_TRACE_DIR` set to an existing API-UID-owned mode-0700 directory and `ORCHESTRATOR_KPF26_TRACE_REQUEST_ID` set to the exact request id. The smoke preparer stores a grant-tagged, random request id in `api-request.json`; set the API environment to that exact value before the owner-bound launch. A single file named by SHA-256 of that id is created exclusively, mode 0600, with full scout summaries, per-scout transport timings, admission notes and raw environment flags; prompts and file contents are not captured. The API response remains unchanged. The directory contains sensitive summaries and must be retained and disposed under the operator's data rules. A duplicate id or trace error cannot overwrite evidence and never changes product behavior; missing or incomplete evidence must not be treated as a gate pass.

Use `kpf26_api_smoke.py ... --trace-dir DIR` to retain and validate that trace against the actual response, the API process tree, request timing and per-summary hashes. It scores full summaries using the pinned scorer, and only reports a task/slot or checkpoint witness if a matching native `/slots` sample was captured during the corresponding call. Raw flags remain raw observations, not asserted feature activation. This remains a single prospective route smoke, not the paired KPF-26 gate; grant, independent window, native runner integration and planning canary requirements remain.

A completed `/chat` route smoke also writes `belief_measurements.jsonl` at capture time. Its `epyc.kpf26.api-observation.v1` row hashes the original `response.bin`, the request and manifest, grant, model and server binary, and projects only the API-reported scout completion count. Runtime flags remain unverified, and the record does not assert fork correctness, outcome quality, pairing, or a gate verdict. Incomplete route runs never write the observation; retain their `result.json` and raw response for diagnosis. Ingest through the existing `kv-prefix-fork` adapter; an actual qualified window and planning-context canary remain separate.
